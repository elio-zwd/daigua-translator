# AI 直接阅读源码制作知识包：试验与交接方案

## 1. 本次要验证什么

验证：不运行专门的符号提取脚本，由 AI 直接阅读 C/H 源码，能否以可接受的工作量，生成有依据、方便复核的中文知识包。

以 `05_createtask` 为首个样本。先独立制作，再与现有知识包比较。当前不开发 Skill；试验后再把有效流程固化为 Skill。

目标是制作有解释价值的词条，并留下文件处理和候选筛选记录。本次不承诺生成编译器级、完整无遗漏的符号数据库。

## 2. 工作方式和输入

AI 在工程目录中按文件、必要时分段阅读源码，结合声明、实现和使用位置解释符号。不把整个工程拼成一个超长输入。

允许使用文件读取、目录枚举、文本搜索、Git、文件哈希、JSON 写入和现有校验器。这里的“直接阅读”是取消符号提取脚本这个前置环节，仍允许这些辅助工具。

不运行 `extractor/extract.py`，不另写正则或语法解析脚本批量生成符号清单。可以用简短脚本保存 AI 已整理的数据或检查 JSON 格式。

| 输入 | 本次建议值或填写规则 |
| --- | --- |
| 翻译器仓库 | `M:\005869\My_Elio\daigua-translator` |
| 源码根目录 | 建议先检查 `D:\FreeRtos\projects\freertos-learning`；这是已有文档中的路径，执行前核实 |
| 课程工程 | `05_createtask` |
| Keil 工程 | `05_createtask/mdk_v5/course.uvprojx`，执行前核实 |
| 构建目标 | 读取工程后记录具体 Target；多个 Target 无法确定时请用户选择 |

如果实际路径不同，先在已知工作目录查找；仍无法定位时向用户询问。不要凭旧路径声称已读取源码。

## 3. 源码范围

先记录范围，再制作词条，避免阅读过程中无边界地扩展。

1. 以所选 Target 的课程源码、课程自有头文件为起点。
2. 纳入该 Target 使用的共享板级、平台适配模块，以及解释这些代码必需的项目配置头文件。
3. 第三方驱动、CMSIS、FreeRTOS 内核默认不批量制作词条。解释项目代码需要时查阅相关声明或实现，记录为“参考读取”。
4. 构建产物、备份、其他课程和未使用的硬件平台不纳入制作范围，记录目录级排除理由。
5. 头文件搜索目录不等于实际依赖。对纳入的共享模块记录工程文件引用、`#include` 或调用等依据。
6. 主要处理 `.c/.h`；如果实际目标依赖 `.cpp/.hpp` 等文件，记录并按相同原则阅读。

构建 Target、宏配置或条件分支无法确定时，保留相关条件，不把它写成当前构建必然发生的行为。无需为了本试验安装编译工具链或执行构建。

## 4. 执行步骤

### A. 建立范围和来源记录

- 阅读工程配置，确定 Target、源码入口和共享模块范围。
- 枚举范围内文件，记录相对路径、用途及纳入理由。
- 记录源码仓库提交号和工作区修改情况；对实际阅读的源码和配置文件保存 SHA-256。
- 源码没有 Git 信息时如实记录，不编造 `source_version`。
- 提交号只说明版本背景；文件哈希用于描述本次实际读取的内容。

### B. 按文件直接阅读并登记候选

完整读完范围内每个文件；长文件分段，记录完成范围。搜索结果、文件开头或节选不代表已读完整文件。

先登记声明和定义，再做收录判断：

- 函数声明与定义，包括文件内静态函数。
- 全局变量和文件内静态变量，包括多变量声明、数组、多行初始化和函数指针变量。
- 局部变量：保留对业务状态、周期、资源、错误处理等有解释价值的变量；短名称也要根据用途判断。
- 宏、枚举、类型：记录对理解项目接口、配置和状态有意义的候选。
- 参数放在所属函数的 `parameters` 中，不重复制作独立词条。
- 结构体成员有独立解释价值时可以作为 `variable` 收录，作用域标明所属类型；否则在类型词条中解释。

一条声明中的多个符号分别登记；使用位置不重复登记为新符号。声明与定义合并后保留两处来源。相同名字但作用域不同的符号分别处理。

本次不要求逐项登记每个普通循环计数器。对此可以按“文件＋函数＋变量名列表”合并记录排除理由。第三方整目录排除也不要求逐个列出其符号。

### C. 结合上下文编写中文

每个收录词条至少核对声明、实现；用途仍不明确时，再看必要的调用或使用位置。

- 函数：做什么、关键参数、返回值或退出行为，以及必要限制。
- 变量：保存什么、所属对象、重要单位，以及必要的初始化或更新方式。
- 宏、枚举、类型：表示什么配置、状态或数据结构。

优先依据实际实现。注释与实现冲突时记录冲突；名称只能作为理解线索。

不要仅凭名称断言线程安全、单位、硬件接线、错误恢复或重复初始化保护。需要推断时写清依据；无法确认的部分放入 `uncertainty`。

说明要简洁，不逐行复述函数。不要为了生成说明而截断必要上下文。

中文名称采用以下规则：

- `name_zh` 使用自然、具体的功能或用途名称，帮助读者理解代码。
- 对以 `config` 开头、且经源码确认表示配置项的标识符，使用“配置：＋具体含义”。前缀使用中文全角冒号 `：`，只添加一次。
- 例如：`configUSE_IDLE_HOOK` → `配置：空闲任务钩子函数开关`；`configUSE_TICK_HOOK` → `配置：系统滴答钩子函数开关`。
- 名称主体保留自然的功能概括，不要求逐词拼接成“配置使用……”或“配置是否使用……”。其他普通宏和符号按自身含义命名，不统一添加“配置：”。
- `description_zh` 解释当前值、对应行为和必要条件。例如当前配置为 `0` 时说明钩子关闭；值变化后按实际源码更新说明。当前值不写进 `name_zh`。
- JSON 中保存名称本身，例如 `配置：空闲任务钩子函数开关`；展示用的 `【】` 由插件添加。

本规则用于后续新生成或用户明确要求修订的知识包。本次只更新方案和交接 prompt，已有 AI 生成的 JSON 保持不变。

### D. 独立复查并冻结初稿

- 再按文件检查一次候选，特别查看多变量声明、多行初始化、函数指针、条件编译及同名局部变量。
- 核对词条位置、作用域、参数和中文解释，检查正文是否存在未经依据支持的断言。
- 检查符合上述规则的 `config...` 配置项是否使用“配置：＋具体含义”，前缀有无遗漏或重复；当前值及行为说明是否与源码一致。
- 运行现有校验器；错误必须修复，警告逐项说明。
- 保存独立初稿为 `pack-initial.json`。后续比较不修改该文件。

在本阶段完成前，不读取旧知识包、旧候选清单和提取器输出。若上下文已包含旧结果，记录已知信息，说明本轮不能视为完全独立试验；不要伪称未接触旧结果。

### E. 与旧结果比较并回看源码

初稿冻结后，才读取：

- `knowledge-packs/05_createtask-pack.json`
- `knowledge-packs/reviews/05_createtask-review.json`
- `knowledge-packs/reviews/05_createtask-review.md`

比较同一源码范围内的收录、排除及中文解释。范围外差异单列。旧结果不是标准答案，每个实质差异都以源码复核：

| 差异 | 处理 |
| --- | --- |
| 旧包有、新包没有 | 判断是漏项、合理排除，还是范围或版本不同 |
| 新包有、旧包没有 | 判断是有效补充还是误识别 |
| 都有但解释不同 | 列出差异、源码依据和判断，必要时保留待确认 |
| 同名词条数量不同 | 检查是否错误合并声明或不同作用域 |

需要修订时生成 `pack-revised.json`，保留初稿，并记录修改原因。旧来源版本与当前源码不同的条目单独标注，不能直接算作新方法的错误。

## 5. 交付物

所有输出写入新试验目录，不覆盖旧知识包、旧复核记录或修改源工程。

### `pack-initial.json`

独立阅读生成的知识包。继续兼容现有格式：

```json
{
  "name": "05_createtask AI 直接阅读试验",
  "version": "0.1.0",
  "description": "AI 根据源码编写，人工语义复核待完成。",
  "entries": [
    {
      "symbol": "Example_Start",
      "kind": "function",
      "name_zh": "启动示例",
      "description_zh": "此处仅展示格式，实际内容必须依据源码填写。",
      "declaration": "void Example_Start(void)",
      "parameters": [],
      "returns_zh": "无返回值",
      "scope": "src/example.c",
      "source": { "file": "src/example.c", "line": 1 },
      "uncertainty": ""
    },
    {
      "symbol": "configUSE_IDLE_HOOK",
      "kind": "macro",
      "name_zh": "配置：空闲任务钩子函数开关",
      "description_zh": "当前配置为 0，不启用空闲任务钩子函数。",
      "declaration": "#define configUSE_IDLE_HOOK 0",
      "scope": "common/include/course_rtos_config.h",
      "source": { "file": "common/include/course_rtos_config.h", "line": 25 },
      "uncertainty": ""
    }
  ]
}
```

以上示例不可直接作为实际词条。`source.file` 相对源码根目录，使用 `/`；行号从 1 开始，取实际声明或定义所在位置。

`kind` 沿用 `function`、`variable`、`macro`、`enum`、`typedef`。原始 `symbol` 保持大小写，不把 `Type.field` 写进名称；所属类型放入 `scope`。

函数和文件层级符号的 `scope` 使用来源文件；局部变量使用“文件::函数:L声明行:C声明列”；成员使用“文件::类型”。合并声明与定义后优先引用实现位置，其他来源记入复核报告。若这些规则仍不能区分符号，保留差异并说明，不按名字强行合并。

### `manifest.json`

保存以下信息：

- 实际源码根目录、工程路径、Target、可确认的宏配置。
- 提交号、工作区修改情况、开始和结束时间，以及所用 AI 模型（可获取时）。
- 文件列表：相对路径、角色（制作词条／参考读取／排除）、理由、阅读状态、已读行范围、实际读取文件的 SHA-256。
- 目录级排除规则、缺失依赖、未解析配置及范围变更记录。
- 是否事先接触旧结果、接触了哪些信息。

执行中发生源码变化时，重读受影响文件并更新相关词条；无法处理完则明确列为未完成。

### `review.md`

面向用户的复核报告，包含：

1. 范围、阅读完成情况、词条数及尚未完成事项。
2. 按文件列出的候选：名称、类别、作用域、来源、收录／排除理由；每个收录词条显示中文说明、参数、返回值和待确认项，方便直接审阅。
3. 支撑重要解释的来源位置，必要的跨文件依据，以及声明合并记录。
4. 校验命令、实际结果、警告说明。
5. 初稿冻结后的差异表、逐项源码复核结论及修订记录。
6. 所有人工复核状态初始为 `pending`；AI 自查和校验通过不能改成人工通过。
7. 处理耗时或可获取的用量信息；拿不到旧方法成本时，不编造效率对比。

需要修订时额外交付 `pack-revised.json`，并对它再次运行校验器。

## 6. 校验和验收

在翻译器仓库根目录运行，替换为实际源码路径和输出路径：

```powershell
python validator/validate.py --pack '实际输出目录\pack-initial.json' --src '实际源码根目录'
```

现有校验器会检查 JSON 结构、必填字段、类别、同作用域重名和来源文件路径等。它不核实来源行是否指向正确符号，也不证明中文正确或符号无遗漏；这些需要直接核对源码。

本轮交付合格的条件：

- 制作范围内的文件都有完整阅读记录，其他文件有明确处理状态。
- 候选收录或排除有理由，同名符号的作用域可区分。
- 收录词条的来源、声明和解释可回到源码核对。
- 中文名称符合第 4 节 C 的命名规则；`config...` 配置项使用“配置：＋具体含义”，当前值及行为在 `description_zh` 中解释。
- 初稿及修订稿（若有）通过现有校验器，警告和未决问题已列出。
- 比较阶段的实质差异均已复核或明确标为未决；未决不伪装成已完成。

不要求新结果凑到旧包的 75 条，也不把旧清单的 149 项当成完整真值。不能以两份清单的数量接近宣称“完整率达到多少”。

试验结论由结果支持：如果直接阅读新增了重要覆盖、解释可靠且复核工作量可接受，可以采用此流程；如果持续出现无提示的漏项，则考虑保留提取器作为辅助对照。一次试验仅验证这个样本，不能证明所有工程均适用。

## 8. 试验完成后如何固化

用户复核本轮结果后，再整理可复用 Skill：输入参数、范围规则、阅读步骤、候选筛选、JSON 格式、校验命令和完成标准。

固化时将第 4 节 C 的中文命名规则及示例纳入 Skill，并保留复查步骤：配置项名称使用“配置：＋具体含义”，描述解释当前值与行为。

Skill 使用通用参数；`05_createtask` 的路径和专有业务解释仅作为示例。本轮若暴露遗漏模式，先调整流程再固化，不直接把未经验证的 prompt 当作稳定方案。

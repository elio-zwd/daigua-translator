# 呆瓜翻译器：项目目的与三步发展规划

更新日期：2026-11-06

文档性质：供用户修改、供后续 AI 接手的项目方向与阶段规划。

当前基线：插件 0.3.0，Git 提交 `f8910af`。

## 1. 给接手 AI 的说明

开始工作前，先理解本文的项目目的，再检查实际代码、用户对本文的最新修改和本次任务要求。本文中的未来规划不代表功能已经实现，也不表示用户要求一次完成全部阶段。

每个阶段开始前，与用户对齐本次范围和验收标准；阶段完成后，根据实际结果与用户复核，再确定下一步。具体流程见第 7 节。

用户可以直接增删本文。重新接手时必须重新读取，不能把早期讨论当作永久固定的需求。文档与实际代码不一致时，说明差异；方向性冲突按用户最新明确指令对齐。

## 2. 项目目的与目标用户

**核心目的：帮助英文基础较弱的开发者准确理解代码中函数、变量等英文名称，并在日常使用中辅助学习英语。**

用户看到英文标识符时，即使不认识其中的单词，也应能通过插件获得有依据、符合项目上下文的中文解释。用户可以自行对照原始英文名称和中文说明学习，不要求插件新增逐词中文释义区域。

当前主要服务于 MCU C/C++ 工程阅读，覆盖函数、变量、参数，以及有理解价值的宏、枚举和类型。注释、字符串、选区和普通技术文本翻译用于辅助读代码。

项目希望达到以下体验：

- 已收录的符号能够快速显示项目中的中文名称、用途、必要参数和来源。
- 项目说明与普通名称翻译有清楚的来源标识，用户能判断解释依据。
- 音标帮助用户学习发音，不改变已经认可的中文解释方式。
- 配置简单，能看清正在使用哪些知识包，以及数据是否正常加载。
- 本地查询可离线使用；联网翻译可关闭，缺少可选信息不阻塞阅读。

## 3. 已确认的产品与开发原则

### 3.1 中文解释沿用现有方式

以现有 AI prompt 根据源码生成的 `name_zh`、`description_zh` 及参数等说明为主。保留自然、具体的中文名称和实际用途说明，不新增单独的逐词中文释义区域。

对于经源码确认表示配置项的 `config...` 标识符，中文名称采用“配置：＋具体含义”，例如“配置：空闲任务钩子函数开关”。当前值和对应行为写在说明中。

知识包中的项目用途应有源码依据。普通词语翻译不能证明函数实际做什么；不确定之处明确保留待确认说明。

### 3.2 音标作为新增信息

在原有中文内容下另起一行，显示“音标（英式优先）”。不改写原有中文名称、功能说明或原始标识符。

复合名称按组成词依次标注读音，例如 `Motor_Start` 分别标注 `Motor` 和 `Start`。这里按词标注的是读音，不增加逐词中文解释。缩写、型号、数字或无法确认读法的部分不强行编造音标。

音标制作流程：

1. 外部 AI 按现有 prompt 阅读源码并生成中文知识包。
2. 补充脚本从用户提供的 ECDict 数据中提取音标，添加可选音标信息并记录来源。
3. 脚本导出未找到音标的词清单。
4. 由用户正在使用的外部 AI 补齐缺失项；仍不能确认的保留缺失或待确认状态。
5. 回填、校验后生成单独的增强版 JSON，保留原始 JSON。

脚本只负责音标补充，不把符号提取脚本重新设为 AI 制包的必要前置步骤。运行时插件读取补充后的数据，不需要直接读取完整 ECDict，也不需要配置 AI 模型或密钥。

[ECDict 官方数据格式](https://github.com/skywind3000/ECDICT#数据格式)将 `phonetic` 描述为“音标，以英语英标为主”，没有分别列出英式、美式字段。因此使用“英式优先”的标注，保留 ECDict 或 AI 补充等来源，不宣称所有记录均已核实口音。

旧 JSON 没有音标时继续正常使用。音标缺失不影响已有中文查询，不因缺失而让整个知识包失效。具体可选字段、拆词方法和补充脚本接口在实施该阶段前结合实际数据对齐。

### 3.3 未收录名称也能提供帮助

对于没有本地知识包词条的函数名或变量名，允许提供普通名称释义，明确标注翻译来源及“用途未核对”。不要把普通名称翻译包装成已确认的项目功能说明。

处理必须遵守联网开关。关闭联网翻译时，不擅自发起网络请求；无法给出有依据的结果时明确提示，不用猜测填充。

### 3.4 简单化、高内聚、低耦合

- 知识包制作、音标补充、本地查询、联网翻译和界面展示分别承担清晰职责。
- 优先完成能验证价值的最小流程，再根据用户反馈扩展。
- 公共逻辑集中复用，避免悬停、右键和命令入口各自维护一套匹配规则。
- 增加信息时优先兼容现有 JSON，不为规划提前建设复杂平台。
- 最终交付以 Windows 10 x64 运行要求为准；调用 PowerShell 使用 `pwsh.exe`。

## 5. 三步发展规划

以下阶段是方向和验收依据，不提前固定全部界面、字段、实现方式或版本号。开始每个阶段时，先确认哪些内容已经完成、哪些仍需实施。

### 第一步：完成独立使用

**目标：**用户不安装 MTranCode，也能完成常用的代码知识查询和文本翻译，并使用音标辅助学习。

**主要能力：**

- 完善独立悬停、选区及普通文本翻译入口，集中复用本地查询和联网翻译能力。
- 统一结果来源标识，避免自身重复展示或再次翻译已经生成的本地说明。
- 对未收录名称提供带来源和“用途未核对”标记的普通名称释义。
- 建立“ECDict 补音标 → 缺失清单 → 外部 AI 补齐 → 增强版 JSON → 离线展示”的最小流程。
- 保留现有快捷设置、诊断、联网开关和旧包兼容能力。
- 开始独立改造前，用 `archive/mtrancode-v0.3` 分支保存确认过的当前 MTranCode 版本；本文记录的基线为 `f8910af`。独立主线移除 MTranCode 集成，旧分支可继续使用原有能力，但不再维护，也不要求把后续主线功能同步回去。

**暂不包含：**全面复制 MTranCode 的全部功能；高级学习系统；为音标补充配置自动调用 AI 的平台。本文创建时不执行分支归档或插件改造。

**验收场景：**

- 未安装或已停用 MTranCode 时，已收录符号仍显示原有中文说明，选区及普通文本翻译入口可独立使用。
- 呆瓜自身只提供一份对应的本地说明，来源标识清楚；与其他插件的冲突有可理解的指引，不擅自修改其他插件设置。
- 有音标的词条换行显示音标；复合名称按词显示；无音标的旧包仍正常查询。
- 音标增强后原始 JSON 保留，中文说明不被补音标流程改写，缺失项和来源可检查。
- 未收录名称的普通释义明确标记用途未核对；关闭联网后不发起新的联网翻译请求。

### 第二步：提高解释准确性

**目标：**解释用户当前正在看的符号，减少同名函数、变量和参数带来的混淆，并使结果便于核对。

**主要能力：**

- 利用当前文件、函数和已知作用域改善候选匹配。
- 无法可靠区分时显示候选及依据，不强行自动选定。
- 提供源码定位，以及知识包版本或源码变化提示。
- 保留项目用途、普通名称释义、音标各自的信息来源和待确认状态。

**暂不包含：**未经验证就承诺完整 C/C++ 语义解析；仅凭名称推断实际功能；在插件运行时自动生成已核实的项目用途。

**验收场景：**

- 不同文件或函数内的同名符号不被错误合并。
- 有足够上下文时优先显示对应结果，并能解释匹配依据；依据不足时展示候选。
- 用户可定位到对应源码；路径缺失、版本不符或来源变化时有明确提示。
- 自动匹配和测试通过不会把人工复核状态改为已确认。

### 第三步：完善知识包管理

**目标：**用户方便地查看、管理工程数据，分别了解单词、函数和变量在工程中的出现频率与自己的查询频率，确定阅读和学习重点；同时知道查询结果来自哪里，并能把缺失内容交给外部 AI 补充。

**主要能力：**

- 提供侧边栏，集中查看、搜索、导入、启用、停用和替换知识包。
- 显示当前工程使用的包、词条数量、来源和加载状态。
- 分别展示工程出现频率和用户查询频率：前者帮助识别工程中经常出现的名称，后者帮助识别用户经常查看、需要重点学习的名称；不合并成一个频率指标。
- 单词与完整函数名、变量名分开统计和展示，保留必要的符号作用域。具体源码统计范围、查询计数及自动悬停的重复计数规则，在第三步开始前结合实际情况与用户对齐。
- 查看词条详情、待确认内容及未命中名称，方便整理后交给外部 AI。
- 与现有文件选择、自动重载、加载诊断和查询逻辑复用，避免重复维护。

**暂不包含：**插件内批量 AI 制包平台、云端账户与同步平台、复杂知识包编辑工作流。是否增加编辑能力根据使用反馈另行对齐。

**验收场景：**

- 用户能确认当前工程正在使用哪些数据，并查看某个结果的来源。
- 用户能分别查看工程高频名称和自己经常查询的名称，明确每项统计的口径；同名单词、不同作用域符号及重复悬停不会被无说明地混为一个计数。英语通用词频不替代这两项指标。
- 包的启停与替换及时反映在查询结果中，失败时保留可解释的状态和原因。
- 用户能查到需要复核或补充的内容，方便交接给外部 AI。

## 6. 当前不列为承诺的扩展

插件内批量 AI 制包平台、音频播放、复杂学习系统，以及超出当前 MCU C/C++ 阅读需求的大规模功能扩展，不列为本轮三步规划的承诺。用户以后提出需求时再评估价值和复杂度。

## 7. 后续 AI 的需求对齐与交付流程

### 阶段开始前

1. 重新读取本文、仓库约束和相关代码，检查用户对文档的最新增删。
2. 说明当前状态、与文档的差异、建议实施范围和可验证的完成标准。
3. 将影响项目目标、使用体验、数据兼容或职责边界的关键不确定项与用户对齐。
4. 对齐后推进本阶段工作。已经确认且仍适用的要求不反复询问；代码检查能确定的事实先自行检查。

音标阶段应核实用户提供的 ECDict 路径与格式，再确认可选字段、复合名称拆分、缺失清单及回填方式。独立化阶段应核实归档基线与分支状态，再开展主线改造。

### 阶段进行中

- 朝已确认的目标推进，保持简单化、高内聚、低耦合。
- 出现影响目标、体验或兼容性的变化时，说明原因并重新对齐，不悄悄扩大范围。
- 区分有依据的事实、推断和待确认事项；保持验证记录可回查。

### 阶段完成后

向用户说明：实际完成的能力、自动测试及人工验收状态、与规划的差异、未决问题和下一步建议。

根据实际使用结果与用户复核，记录用户反馈并调整后续规划，再确定下一阶段。不能仅以构建成功或测试通过替代用户体验复核，也不自动连续实施全部三步。

### 文档维护

用户对本文的增删是后续规划的重要输入。接手 AI 必须读取最新版本，对存在冲突或不明确之处与用户对齐。实际工作结束时，在本次授权范围内记录阶段进度、验证证据和仍未解决的问题，保持“已实现”与“未来目标”分开。

本次文档交付仅创建本文，不修改插件、既有知识包或 Git 分支，不自动提交或推送。
